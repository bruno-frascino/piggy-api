# 0004. PDF generation via pdfkit, not Puppeteer/Chromium

- **Status**: Accepted
- **Date**: 2026-07-24 (retro-documented 2026-07-28)

## Context

Tax reports need to be rendered as downloadable PDFs. The common approach for
data/HTML-heavy PDFs is a headless-Chromium tool (Puppeteer/Playwright) rendering an HTML
template to PDF. The production API runs on a VPS with only 1-2GB RAM (see
`/memories/repo/vps-deploy-setup.md` for the full deploy setup).

## Decision

PDFs are generated with `pdfkit` — a pure-JS, low-level PDF drawing library — instead of
Puppeteer/Chromium. `piggy-api/src/lib/pdf-report.ts` draws the report programmatically
(text, tables, layout) rather than rendering HTML/CSS. Generated bytes are stored directly
in the `TaxReport.pdfData` Postgres `Bytes` column (no S3/disk storage), served via
`GET /api/tax-reports/:id/download`.

## Consequences

- No Chromium binary/sandbox to install, patch, or run on the constrained VPS — avoids the
  memory spikes and cold-start cost of a headless browser per report.
- Layout is coded by hand (coordinates, tables) rather than styled with CSS — more verbose
  for complex layouts, but predictable memory/CPU cost per report.
- Storing PDF bytes in Postgres (not S3) trades some DB size growth for zero extra
  infrastructure — acceptable at this system's scale (personal use, not high-volume SaaS).
- Email delivery of the PDF was deliberately deferred/not implemented (download-only) —
  revisit this ADR if that requirement is added.
